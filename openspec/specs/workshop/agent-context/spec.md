# workshop/agent-context Specification

## Purpose
Keeps the standing context every coding agent loads in one deliberately small file that participants grow themselves, and makes the spec-driven workflow available to every agent the workshop supports.

## Requirements

### Requirement: One context file
`AGENTS.md` SHALL be the single source of standing project context. Agent-specific entry points SHALL only reference it and MUST NOT duplicate its content.

#### Scenario: Claude Code in the repository
- **WHEN** Claude Code starts in the repository root
- **THEN** its loaded context contains the content of `AGENTS.md` through the entry point's reference

#### Scenario: No duplicated context
- **WHEN** the agent entry points are compared with `AGENTS.md`
- **THEN** none of them repeats a statement from it

### Requirement: Deliberately thin starting state
On the main branch, `AGENTS.md` SHALL state only what the repository is, how to install it and run the suite, how to reach the shop, and that Lab 2 builds the file out. It MUST NOT contain conventions, shop behaviour or tool habits that later labs teach, and MUST stay under 30 lines.

#### Scenario: Measuring the starting state
- **WHEN** `AGENTS.md` on the main branch is inspected
- **THEN** it has fewer than 30 lines and names none of the conventions or RobotCode habits taught in Labs 2 to 4

### Requirement: Spec-driven workflow for every supported agent
The OpenSpec workflow - explore, propose, apply and archive - SHALL be available as native commands or skills for Claude Code, Codex and GitHub Copilot, generated by the pinned OpenSpec version.

#### Scenario: Proposing from each agent
- **WHEN** a participant using Claude Code, Codex or GitHub Copilot looks for the propose workflow
- **THEN** the agent offers it as a command or skill

### Requirement: Spec namespaces
The OpenSpec configuration SHALL describe three namespaces: `shop/*` for the behaviour of the shop, which agents use as reference when writing tests; `suite/*` for what a participant's own tests verify, where the changes participants propose in Module 5 write their specs; and `workshop/*` for the guarantees of this repository, which participants' agents do not need. A change that adds or changes tests MUST NOT write to `shop/*` or `workshop/*`.

#### Scenario: Context for a new artifact
- **WHEN** an agent requests the instructions for any OpenSpec artifact
- **THEN** the returned project context explains the three namespaces, which one describes the shop, and which one a change that adds tests writes to

#### Scenario: A participant proposes tests for a story
- **WHEN** a participant proposes a change that automates criteria of a shop story
- **THEN** the change's delta specs are created under `suite/*`, and the main specs under `shop/*` and `workshop/*` are unchanged by its archive

### Requirement: Neutral shop specifications
The OpenSpec configuration SHALL carry, as a rule for spec artifacts, that requirements under `shop/*` describe correct behaviour only and never name a feature flag, a locator stage, a planted bug, a locator or the purpose of a check. The rule MUST be scoped to `shop/*` so that it does not constrain `workshop/*`.

#### Scenario: Writing a shop spec
- **WHEN** an agent requests the instructions for a spec artifact
- **THEN** the returned rules include the neutrality rule for `shop/*`

### Requirement: No secrets in context or configuration
Context files, agent entry points and OpenSpec configuration SHALL contain no credential, token or API key. Secrets SHALL live only in the git-ignored `.env` file, and the committed `.env.example` SHALL list setting names without values.

#### Scenario: Scanning the repository
- **WHEN** the tracked files of the repository are scanned for secrets
- **THEN** no credential, token or API key is found

#### Scenario: A local .env with secrets
- **WHEN** a participant stores an API key in `.env`
- **THEN** git does not track the file
